# Migration: Alchemy → Openfort

## Goal
Add Openfort as the auth provider for etherplay-connect via a minimal interface abstraction. The `web/login` popup service will use whichever provider is configured via env var (`VITE_AUTH_PROVIDER=openfort` or `alchemy`). Alchemy package stays completely untouched. Demos stay unchanged — buttons work as-is, and `web/login` uses whichever provider is configured.

## Current Architecture

```
@etherplay/connect (main connector)
  |-- @etherplay/connect-core (types: AlchemyMechanism, OriginAccount)
  |-- @etherplay/alchemy (social login wrapper around @account-kit/signer)
  |     |-- @account-kit/signer ^4.13.0 (Alchemy Account Kit)
  |-- @etherplay/wallet-connector
  |-- @etherplay/wallet-connector-ethereum
  |-- web/login (popup login service)

Flow: connect() → popup → web/login → Alchemy auth → derive origin account → postMessage back
```

## Target Architecture

```
@etherplay/connect (main connector)
  |-- @etherplay/connect-core (types + AuthProvider interface)
  |-- @etherplay/auth-provider (abstract interface for auth backends)
  |-- @etherplay/openfort (Openfort implementation of interface)
  |     |-- @openfort/openfort-js
  |-- @etherplay/alchemy (UNCHANGED — untouched)
  |-- @etherplay/wallet-connector
  |-- @etherplay/wallet-connector-ethereum
  |-- web/login (popup login service — provider selected by env var)

Flow: connect() → popup → web/login → (Openfort OR Alchemy, configured by env) → derive origin account → postMessage back
```

## Design Principle

- `@etherplay/auth-provider` defines the interface contract
- `web/login` uses the interface, NOT a concrete implementation directly
- `@etherplay/openfort` implements the interface (for when `VITE_AUTH_PROVIDER=openfort`)
- Alchemy implementation would go in a separate package (not built yet, but the interface supports it)
- `web/.env` has `VITE_AUTH_PROVIDER=openfort` to select Openfort at runtime
- Demos never change — they just call `connect({type: 'email'})` etc., and `web/login` handles provider selection internally

## New Package: `@etherplay/auth-provider`

Minimal interface in `packages/etherplay-auth-provider/` that defines the contract for auth backends.

**`src/types.ts`** - Auth backend interface:

```typescript
export type AuthProviderSettings = {
  walletHost: string;
  // Provider-specific settings (filled by implementation)
  [key: string]: unknown;
};

// Result returned after successful auth — matches OriginAccount structure
export type AuthResult = {
  address: `0x${string}`;
  signer: {
    origin: string;
    address: `0x${string}`;
    publicKey: `0x${string}`;
    privateKey: `0x${string}`;
    mnemonicKey: `0x${string}`;
  };
  metadata: Record<string, unknown>;
  mechanismUsed: Mechanism;
  savedPublicKeyPublicationSignature: `0x${string}` | undefined;
  accountType: string;
};

// Mechanism types — same shape as existing types in connect-core
export type AuthMechanism = EmailMechanism | OauthMechanism | MnemonicMechanism;

export type EmailMechanism = {
  type: 'email';
  email?: string;
  mode?: 'otp';
};

export type OauthMechanism = {
  type: 'oauth';
  provider: { id: string; connection?: string };  // id: 'google', 'facebook', 'twitter', 'discord', 'apple', etc.
  usePopup?: boolean;  // true = open in same popup window, false = redirect
};

export type MnemonicMechanism = {
  type: 'mnemonic';
  mnemonic?: string;
  index?: number;
};

// State machine for the popup auth flow
export type AuthState =
  | { step: 'Idle' }
  | { step: 'EmailToProvide' }
  | { step: 'WaitingForOTP'; email: string }
  | { step: 'VerifyingOTP'; email: string }
  | { step: 'ConfirmOAuth'; provider: string }
  | { step: 'WaitingForOAuthResponse' }
  | { step: 'GeneratingAccount' }
  | { step: 'SignedIn'; result: AuthResult }
  | { step: 'Error'; message: string };

// The interface that auth backends must implement
export interface AuthProvider {
  init(settings: AuthProviderSettings): Promise<void>;
  // Start auth flow for given mechanism
  connect(mechanism: AuthMechanism): Promise<void>;
  // Provide OTP code (for email flow)
  provideOTP(otp: string): Promise<void>;
  // Confirm OAuth (for popup-based OAuth, after callback detected)
  confirmOAuth(): Promise<void>;
  // Get current state
  getState(): AuthState;
}
```

**`src/index.ts`** - Re-exports all types.

**`src/index.ts`** - `createOpenfortProvider()`:

```typescript
// Creates an AuthProvider backed by Openfort SDK
export function createOpenfortProvider(settings: {
  walletHost: string;
  publishableKey: string;
  shieldPublishableKey?: string;
  chainId: number;
  // ... same options as createAlchemyConnection
}): AuthProvider {
  // Initialize Openfort SDK
  const openfort = new Openfort({
    baseConfiguration: { publishableKey: settings.publishableKey },
    shieldConfiguration: settings.shieldPublishableKey
      ? { shieldPublishableKey: settings.shieldPublishableKey }
      : undefined,
  });
  await openfort.waitForInitialization();
  
  // ... implement AuthProvider interface methods
}
```

**Key implementation details:**

### Email OTP flow:
1. `connect({type: 'email', email})` → calls `openfort.auth.requestEmailOtp({ email })`
2. State → `WaitingForOTP`
3. `provideOTP(otp)` → calls `openfort.auth.logInWithEmailOtp({ email, otp })`
4. Authenticated, embedded wallet created
5. Sign origin key message: `openfort.embeddedWallet.signMessage(originKeyMessage(origin))`
6. Derive origin account from signature (same as current: `fromSignatureToKey` → `fromEntropyKeyToMnemonic` → HD key derivation)
7. State → `SignedIn` with result

### OAuth flow (popup-based, `usePopup: true`):
1. `connect({type: 'oauth', provider: {id: 'google'}, usePopup: true})`
2. Calls `openfort.auth.initOAuth({ provider: OAuthProvider.GOOGLE, redirectTo: popupCallbackURL })`
   - `popupCallbackURL` = the popup's current URL (e.g., `https://web-host.com/login/?type=oauth-redirect`)
3. Returns OAuth authorization URL
4. **Same popup window**: `popupRef?.contentWindow!.location.href = oauthUrl` (replaces the popup's content with OAuth page)
5. User completes OAuth on Google etc.
6. Openfort redirects to `popupCallbackURL?token=...&user_id=...`
7. **Opener polls** `popupRef?.contentWindow?.location.href` to detect callback URL
8. Extract `token` and `user_id`, call `confirmOAuth()` which calls `openfort.auth.storeCredentials({ token, userId })`
9. Sign origin key + derive origin account
10. State → `SignedIn` with result

### OAuth flow (redirect-based, `usePopup: false`):
1. `connect({type: 'oauth', provider: {id: 'google'}, usePopup: false})`
2. Calls `openfort.auth.initOAuth({ provider: OAuthProvider.GOOGLE, redirectTo: appCallbackURL })`
3. Redirects browser to OAuth URL
4. After OAuth, browser redirects back to `appCallbackURL` with `?token=...&user_id=...`
5. Callback page calls `storeCredentials()` and continues flow

### Mnemonic flow (custom, not through Openfort SDK):
- Mnemonic auth is NOT handled by Openfort SDK
- The popup handles mnemonic auth the same way as before (custom logic, no SDK calls)
- After mnemonic auth, derive origin account and post result
- This is a hybrid: `AuthProvider` interface for email/oauth, custom flow for mnemonic

### Auth0:
- **Removed** - not supported by Openfort, not implemented in Openfort provider

## Changes to `web/login`

**`web/.env`**:
```
VITE_AUTH_PROVIDER=openfort  # or 'alchemy' — selects which provider implementation to use
VITE_OPENFORT_PUBLISHABLE_KEY=
VITE_OPENFORT_SHIELD_PUBLISHABLE_KEY=
# Alchemy vars still present but only used when VITE_AUTH_PROVIDER=alchemy
VITE_ALCHEMY_RPC_URL=
VITE_ALCHEMY_API_KEY_NOT_RECOMMENDED=
```

**`web/login/src/lib/state.ts`**:
- Read `VITE_AUTH_PROVIDER` from env
- Dynamically create the provider instance:
  - If `openfort`: call `createOpenfortProvider()` with Openfort credentials
  - If `alchemy`: call `createAlchemyConnection()` (existing code)
- The rest of state management stays the same (uses the interface)

**`web/login/src/lib/handler.ts`**:
- Provider-agnostic routing — routes mechanisms to the provider's interface
- `email` → `provider.connect({type: 'email', email, mode: 'otp'})` → `provider.provideOTP(otp)`
- `oauth` → `provider.connect({type: 'oauth', provider: {id}, usePopup: true/false})` → `provider.confirmOAuth()`
- `oauth-redirect` → `provider.confirmOAuth()` (reads token/user_id from URL params)
- `mnemonic` → custom flow (not through provider interface)
- `magicLink` → remove (not supported by Openfort)
- Auth0 → remove

**`web/login/src/lib/Login.svelte`**:
- Communicates with opener via `postMessage` — unchanged protocol
- State machine uses the provider interface — unchanged

**`web/login/src/lib/mechanism/Email.svelte`**:
- Calls `authProvider.connect({type: 'email', email, mode: 'otp'})`
- Calls `authProvider.provideOTP(otp)`
- Implementation-agnostic (works with OpenFort or Alchemy)

**`web/login/src/lib/mechanism/OAuth.svelte`**:
- Calls `authProvider.connect({type: 'oauth', provider: {id}, usePopup})`
- If `usePopup: true`:
  - Get OAuth URL from provider
  - Navigate same popup: `popupRef?.contentWindow!.location.href = oauthUrl`
  - Poll popup location for callback detection
  - Call `authProvider.confirmOAuth()` when callback detected
- If `usePopup: false`:
  - Get OAuth URL from provider
  - Redirect current window: `window.location.href = oauthUrl`

**`web/login/src/lib/mechanism/Mnemonic.svelte`**:
- **Keep unchanged** — custom flow outside provider interface

## Key Technical Notes

1. **Popup OAuth (`usePopup: true`)**: Openfort `initOAuth()` returns OAuth URL. Navigate the same popup: `popupRef?.contentWindow!.location.href = oauthUrl`. Poll `popupRef?.contentWindow?.location.href` to detect callback `?token=&user_id=`. Then call `confirmOAuth()` → `storeCredentials()`.

2. **Redirect OAuth (`usePopup: false`)**: Openfort `initOAuth()` returns OAuth URL. Redirect current window: `window.location.href = oauthUrl`. After callback, page calls `storeCredentials()` and continues.

3. **Provider selection**: `web/.env` has `VITE_AUTH_PROVIDER=openfort`. `web/login` reads this at startup and creates the matching provider. The interface is the same regardless of backend.

4. **Origin account derivation**: Unchanged. Still signs `originKeyMessage(origin)` with embedded wallet's `signMessage()`, then derives HD key from signature via `fromSignatureToKey` → `fromEntropyKeyToMnemonic` → HD key derivation.

5. **Mnemonic flow**: Custom flow outside the provider interface. The popup handles it independently, then posts result back.

6. **Demos unchanged**: Demo buttons call `connect()` with mechanism types. The popup handles provider selection internally via env config. No demo code changes needed.

7. **Alchemy untouched**: The Alchemy package (`packages/etherplay-alchemy/`) is never modified. It stays as-is for existing users. The interface design allows an Alchemy implementation to be built later if needed.
