'@etherplay/delegation': patch
---

Build `Delegation.message()` in two parts, so the package compiles under its own `production` profile.

`hardhat compile --build-profile production` failed with five copies of `Stack too deep [...] Variable value0 is 3 slot(s) too deep`, which blocked every adopter that compiles with the optimizer on: `jolly-roger`'s `with/local-signer` branch could neither deploy nor run its e2e suite, and `template-commit-reveal` and the games built on it were next.

The cause is not the `runs: 999999` in that profile, and lowering it would not have helped: the original source fails at `runs: 1` just as it does at `999999`, and compiles only with the optimizer **off**. With the optimizer on, solc 0.8.28's legacy pipeline encodes a packed tuple through a generated Yul block that holds every argument on the stack at once, hence the compiler-generated `value0` in an error that names no file. Six dynamic arguments fit and seven do not. `message()` had eight, and `digest()` and `registerViaSignature()` failed only as carriers, by inlining it. The inline assembly in `SignatureUtils.recover` and in `layout()` is not involved; both compile clean in isolation under the same settings.

So the eight-argument `abi.encodePacked` becomes a six-argument field block with the prose prepended to it. The large prose constant stays in the outer call, so only the short field block is copied twice.

**The signed text is unchanged, byte for byte.** Every operand is a `string`, so packed encoding is plain concatenation with no length prefix and no padding, and concatenation is associative: `A | (B | C)` is `A | B | C`. Every signature anyone has produced stays valid. `vectors.json` is what holds that down, and its `builds the exact message` / `builds the exact digest` cases pass under both profiles.

The ERC-7201 `STORAGE_LOCATION`, the `Layout` struct, the ABI and the event are all untouched.

Adopters do get different bytecode, in three functions and no others. `canActFor`, `register`, `revoke` and `statusOf` compile to byte-identical runtime code; `message` grows 126 bytes and `digest` and `registerViaSignature` 58 each. Measured against the same source under `viaIR` (the one optimizing pipeline where the old and new source both compile), the split costs about 217 gas on `registerViaSignature`, roughly 0.3% of a ~76k operation, and nothing at all on `canActFor`. Under the production profile the package now reports `canActFor` 1522, `digest` 47404 and `registerViaSignature` 76092.

`viaIR` was the obvious alternative and was rejected deliberately: it would have fixed the build without touching this source, but it changes generated bytecode for **every** contract in every adopting project rather than three functions in one library, and it cost 39% more cold compile time even on this 14-file package.
